v0.7.0's headline is [**gg**](/gg/overview/) — The Test Cabinet's own coding harness, the
first authored inside this repository rather than integrated from a third party, and a run
mode with its own configuration surface, its own result views, and its own comparison
space. Its full design lives in [its own section](/gg/overview/); these notes cover what
changed in it late in the cycle.

The largest of those changes is that **gg's agent model was rebuilt**. Everything an agent
instance holds — its conversation, its memories, its task list, its handle on the board,
what it has read from the skill catalog, its thread archive — is now a **[module](/gg/modules/)**:
one unit of state with defined rules for what it puts in the prompt, what it reports, how it
is copied, and what happens to it when a different agent takes it over. That single
abstraction is what the rest of this release rests on. Memories gain **scoping** and
**linked instances**, so several agents can curate one store and each is told what the others
wrote. **[FSM processes](/gg/fsms/)** stop being a fixed pair of harness-authored machines
and become a state table anyone can write, each state running an agent profile of their
choosing and each transition naming exactly which modules the next state inherits. And
**[`exec` and `fork`](/gg/fork-and-exec/)** let a model perform the same handoff itself:
become a different agent carrying its whole conversation, or run a copy of itself that
starts already knowing everything it knows.

The same change **deletes plan mode**, the whole planning capability, and the built-in
`tdd` and `plan-first` machines. Equivalent behaviour is now something a configuration
composes rather than something the harness ships.

This remains pre-1.0 software, built first for the people working on the project.

## Features

### Modules: what an agent holds, as a first-class thing

Per-agent state used to be six unrelated types wired together by hand at every spawn site,
each with its own rules for copying that lived only in prose. It is now one
[module](/gg/modules/) abstraction over six closed kinds — `history`, `memories`, `tasks`,
`board`, `skills`, `archive` — and every one of them answers the same five questions: what
it pins in the window, what it streams as telemetry, how it is **forked** (an independent
copy), how it is **shared** (a linked handle on one store), and what has to be re-resolved
when an agent running a different profile **adopts** it.

Making the copy semantics explicit was the point. `#[derive(Clone)]` had meant "deep copy"
on one runtime and "alias the store" on three others, a distinction carried nowhere but in
comments; it is gone from all four, and every copy in the harness now names which of the two
it wants at the call site.

Two rules the abstraction enforces rather than documents: a **fork never duplicates
telemetry** the original has not yet reported, so one write is one event on one stream; and
**caps are re-resolved from the receiving profile** on every transfer, which is the classic
bug a module handed to a stingier agent would otherwise carry.

### Owned and unowned modules

Every module-backed capability now reads an **`ownership`** param — `owned` (the default,
so every stored configuration is unchanged) or `unowned`.

An unowned module contributes nothing to the window: no pinned block, no skills menu, no
linked-memory notice. Everything else is untouched — the tools are still offered, the store
is still read and written, the telemetry still reaches the console, and the prompt still
explains the capability, because a model handed `add_task` with nothing telling it what a
task list is for would use it worse than one told nothing at all. What it stops doing is
handing over the contents on every request.

One case applies it automatically, and it replaces a special case that used to be written
out by hand: an agent whose profile has no project-management capability now holds the
run-global board **unowned**. It is still on the same queue — the issue it was dispatched
for is on that board — and it is still not shown a decomposition it has no tool to act on.

### Memories: four scoping strategies

The [`memories`](/gg/memories/#scoping-whose-memories-are-these) capability gains a
**`scope`** param deciding *which instance* an agent binds to:

| `scope` | Which instance |
| --- | --- |
| `isolated` (default) | A fresh one per agent instance — the previous behaviour, unchanged |
| `shared` | One per agent **profile**, including instances running in parallel |
| `inherited` | Its **spawner's**, read/write, when it was spawned as a subagent; its own otherwise |
| `read-only` | As `inherited`, but this holder may not write |

Two rules make the four coherent, and both are enforced rather than merely stated.
**`read-only` only ever restricts an inherited handle** — an agent that ends up with an
instance of its own under `read-only` (the root, an issue's implementer, a reviewer or judge,
or a subagent whose spawner keeps no memories) may write it, because a private notebook
nobody may write is not a feature. And **write access belongs to the holder, not the store**,
which is precisely why a read-only agent's own `inherited` subagent gets a read/write handle
onto the very same store. Inheritance chains to any depth.

A child that organizes its memories under a different [strategy](/gg/memories/#the-three-strategies)
from its spawner cannot take the spawner's instance — a store is read by the calls its own
strategy offers — so it gets one of its own, and the pairing is reported as a launch warning
rather than left to be inferred later from a notebook that stayed empty.

### Linked instances, and a notice that does not break the prompt cache

When several agents hold one store and one of them adds, revises or removes a memory, every
**other** holder is told in its next prompt — one line per memory, naming what it is and
what happened to it, so the agent can decide whether to read it. Deletions are included,
because acting on a memory that has since been deleted is the failure the notice exists to
prevent. Under `scratchpad`, which has no read call, the notice carries each memory's body
inline rather than pointing at a call the agent does not have.

The **pinned index does not change**. That is the requirement and it is also what keeps the
[prompt cache](/gg/overview/#prompt-caching) intact: the notice is appended at the tail as an
ordinary message, so the whole previous request stays a byte-identical prefix of the next
one. Rebuilding the index instead would rewrite the cached prefix on a turn this agent did
nothing at all, and re-bill the request in full.

Each holder keeps its own watermark, so a notice is delivered exactly once, a holder is
never told about its own writes, and a holder that joins late is not handed a backlog of
everything that happened before it existed. A run in which nothing is linked never produces
a notice and pays nothing for the machinery.

Underneath, the store's destructive pending-revision queue became an **append-only,
author-tagged log with per-holder cursors** — the only shape under which two holders can both
be correct. Attribution is recorded at the mutation rather than guessed at the drain, so a
write is reported once, on the stream of the agent that made it, while every other holder
re-emits its own snapshot: its panel changed, but the work was not its own.

### Read-only holders are gated at the toolset

A read-only holder is offered exactly the read calls and nothing else. The write calls are
never contributed to its toolset, so no schema is shown for one, no program has one in scope,
and the [system prompt](/gg/prompts/) tells it the memories are another agent's rather than
telling it to curate them. Because the gate is by *capability configuration* rather than by
tool name, it covers the [responses-as-code](/gg/responses-as-code/) surface in the same move.

Under `scratchpad` a read-only holder gets no memory tools at all, which is coherent: that
strategy has no read call because its memories *are* the pinned block.

### FSM processes are now yours to write

A profile that enables the [`fsm`](/gg/fsms/) capability is an **FSM shell**: it takes no
turns of its own, and its `states` param is an ordered list of states over the run's *other*
agent profiles. Each state names the profile it runs and its outgoing edges; each edge names
a target state, an optional description the model is shown, and the explicit list of
[modules](/gg/modules/) it transfers. The first state is the entry; a state with no edges is
terminal, and its ending is the machine's return value.

The state's agent is offered a `transition_state` call listing exactly the states it may
move to — the same way `spawn_subagent` lists the agents it may spawn — and naming an
undeclared target is a refusal that lists the legal ones rather than an error that stops the
run. The move is deferred to the end of the turn, exactly as an ending is.

The whole machine is **one agent**: one id in the tree, one scheduler slot, one return value,
so a shell is namable everywhere a profile is — as the run's root, as a `spawn_subagent`
target, as an issue's implementer, as a workflow stage — and whoever put it to work cannot
tell the difference. Per-slot accounting keys on the profile each state actually ran, so a
machine's cost splits per state.

`transfer` is **explicit**, and an absent or empty list carries nothing. A recorded
configuration has to say what it does, and a magic default nobody wrote down is exactly the
sort of decision a reader of the record cannot see. The console's editor pre-fills `history`
on every edge it creates, so the common case is still one click.

Structural mistakes are **launch failures** in the same class as a roster reference naming an
undeclared profile — no `states`, a duplicate or empty state name, a state naming a profile
the set does not declare, an edge naming a state the machine does not declare, or a machine
used as one of its own states. Unrecognized *values* keep falling back with a warning, as
everywhere else in gg.

### Authoring a machine in the console

Turning on the `fsm` capability switches the agent form into a **process editor**: one card
per state, the first badged *entry* and an edge-less one badged *terminal*, with the state's
name, a select over the configuration's other profiles for the agent it runs, and a nested
edge list. Each edge gets a select over the sibling state names, a free-text "when to take
this", and a checkbox per module kind.

Two affordances exist because the mistakes they prevent are silent ones: **Make entry** moves
a state to the front rather than asking anyone to reorder rows, and **renaming a state carries
its inbound edges**, since a rename that left them behind would produce the "a transition
names a state that does not exist" launch failure one field away from where it was caused.
The editor refuses to save what gg would refuse to launch, in the same words and beside the
row that has to change.

### `exec` — become another agent

The new opt-in **`agent-transitions`** capability contributes two calls, each separately
withholdable through [toolset ablation](/gg/toolset-ablation/).

[`exec`](/gg/fork-and-exec/) replaces the running agent with one running another profile from
its own delegation roster — the same allowlist `spawn_subagent` is checked against, because
putting a profile to work is putting a profile to work. Every module both profiles have is
**transferred**, `history` above all, so the successor does not get caught up: it simply
continues. What the successor's profile turns off is **dropped**, what only it has is
**initialized fresh**, and the successor is *told* all three in an opening note, along with
whatever the call's `prompt` said.

Naming an FSM shell **enters that machine** at its entry state, which is how a plain agent
hands its work to a declared process. The reverse is refused: an agent already standing in a
state is not offered `exec` at all, because inside a process the next move belongs to the
process.

A succession is **one agent throughout**: one scheduler slot, one return value, a fresh id per
incarnation (so each stream is self-contained for the console's per-agent reduction), the same
depth (the depth cap exists to bound delegation, and a chain of execs that exhausted it would
be measuring the wrong thing), and **one** turn ceiling spent between the incarnations rather
than one each.

The successor's compaction check runs before its first turn against **its own** window limit,
so an agent that filled a million-token window and then became one on a 32k model compacts
immediately. gg deliberately does no more than that: if two profiles' windows differ greatly,
the answer is a [compaction](/gg/compaction/) strategy whose summarizer runs on a separate
model, and that is a configuration decision.

### `fork` — run a copy of yourself

[`fork`](/gg/fork-and-exec/) takes a prompt — what the copy should do that you will not — and
produces an ordinary child: its own id one level deeper, its own scheduler slot, the same
depth and parallelism caps, and the same `wait_for_subagents` / `send_message` handles every
other subagent has. It takes no `agent`, because a copy can only ever be the agent making it,
and that is the whole point: a subagent opens on a brief somebody had to write, a copy opens
already holding everything its forker worked out.

Everything is cloned — nothing dropped, nothing empty, since the copy runs the very profile
the original does. Memories are the exception and follow the forker's scope: an `isolated`
notebook is copied and the two diverge, while every scope that links agents at all stays
linked across the fork. A fork is not a reason to split what a configuration deliberately
joined.

Because a copy has to be collectable, `fork` is offered only to a profile that also carries
[subagents](/gg/subagents/) or [workflows](/gg/workflows/). A copy nobody can wait on or
message is a leak rather than a second worker.

### Both are turn-final

A call **declares**; the loop **applies**, once every tool result of the turn is recorded.
That is not a convenience: a window rewritten or copied mid-turn would carry an assistant
message whose tool results had not been written yet, which an OpenAI-shaped provider rejects
outright — and under [responses-as-code](/gg/responses-as-code/) it would pull the very window
a running program is composing into out from under it.

Two consequences the tool descriptions state outright. A **fork cannot be waited on in the
turn that created it** (its id is real from the moment the call returns; it is not a child
until the turn ends). And a **turn makes one succession** — the first `exec` or
`transition_state` stands and a second is refused, because an invisibly replaced successor
identity is a change the model cannot see. An ending declared in the same turn beats both.
Forks are the exception to first-wins: they are additive, so a turn may declare several.

Under responses-as-code all three are real bound calls: `agents.exec` and
`agents.transitionState` are deferred declarations, the shape `context.compact` already had,
and `agents.fork` returns the copy's id immediately.

### Reading a succession in the console

The Instances explorer no longer draws every agent as a spawn. An agent that **succeeded**
another hangs directly off its predecessor's folder, tagged with where it came from
(`⇢ verify`, `⇢ exec`), so a chain of incarnations reads as the one lineage it is; only
genuinely spawned agents go under `subagents`, a fork among them, tagged `⑂ fork` so a copy
reads as a copy. Each arriving agent's Overview states what it inherited — the state entered,
and which modules were carried, dropped and started fresh — and both halves of a handoff
appear in the activity feed on the streams they landed on.

The root's Overview gains a **process strip** showing the states a machine walked and what
each transition carried. The memories panel gains its holder's scope and, on a linked
instance, marks the memories **another** holder wrote — attribution the run's own revision
stream already carried, surfaced rather than averaged away.

## Removals

### Plan mode and the planning capability

The whole `planning` capability is gone: the capability id, its `enter_plan_mode` and
`submit_plan` tools, its prompt templates, its telemetry, its `plan` context band, and the
console's plan view. A run's read-only planning pass and its fresh-context reset into
implementation are now something a configuration composes as an FSM — two states, an explore
profile with no write tools and a build profile, and an edge between them naming what
carries.

### The built-in `tdd` and `plan-first` machines

gg's first FSM engine shipped a small library of **harness-authored** machines selected by a
`machine` param. Both are gone, along with the `advance_state` tool. A machine only the
harness can author is a machine only the harness can study, and a fixed pair of built-ins was
an answer to a question a configuration should be able to ask for itself.

Because `enter_plan_mode`, `submit_plan` and `advance_state` were the *entire* contents of
gg's turn-level tool class, that class is gone too — with it the WIT `turns` interface and
the "some tools are not bound into a program's scope" caveat. Every one of gg's thirty-seven
tools is now bound.

## Breaking changes

There is no backwards-compatibility shim for any of these, deliberately. Historical runs
render nothing for the removed panels, which is accepted.

- **The `planning` capability is removed.** A stored set naming it still deserializes and is
  ignored; it now earns a launch **warning** naming what replaced it, so a sweep that still
  enables it is loud rather than silent.
- **`fsm.machine` no longer means anything, and an enabled `fsm` with no `states` is a hard
  launch failure.** `"machine": "tdd"` therefore *fails to launch* rather than quietly
  running as an ordinary single agent. This is the one intentional hard break: a run recorded
  as "the TDD arm" that was nothing of the sort would poison every comparison drawn from it.
- **`GgContextSource::Plan` is removed** (the enum is 10 members, was 11), and the
  `planning` telemetry kind with it.
- **`fsm_state` telemetry is redefined** from `{ machine, state, stateIndex }` to
  `{ fsm, state, agent, from }`. An old record's event is dropped by the console's reducer.
- **The tool vocabulary changed**: `enter_plan_mode`, `submit_plan` and `advance_state` are
  removed; `transition_state`, `exec` and `fork` are added. A stored `disabledTools` naming a
  removed tool now produces the ordinary "unknown disabled tool" launch warning.

Everything else in this release is additive, and absent means the previous behaviour:
`agent-transitions` is off by default, `memories.scope` defaults to `isolated`,
`<module>.ownership` defaults to `owned`, the new `agent_transition` telemetry kind is new,
and `memory_state`'s `scope` and `writable` fields are defaulted so a record written before
them still parses.

## Fixes

### A read-only memory holder could wedge its own run

`memory-compaction` — the strategy that asks an agent to record its working state as memories
instead of writing a summary — was demoted to the default only when memories were switched
**off**. An agent holding somebody else's memories read-only would therefore be told to record
its state with calls it does not have, and the pending compaction could never be satisfied:
the run would sit against a full window until a ceiling stopped it. The gate now asks whether
the agent may *write* its memories, not whether it has any, and the demotion is reported as a
launch warning.

### Four transition refusals were unreadable

The refusals `transition_state` answers an illegal move with had been written without line
continuations, so a model was reading runs of thirty literal spaces mid-sentence. They are
joined properly now.
