Two things The Test Cabinet did still ran off to the side of the cluster: a run's
public release was driven from an operator's own machine by `tcab publish`, and
the [web console](/components/web/overview/) was a separate static deploy (or a
host `npm run dev`). v0.3.3 pulls both onto the cluster. Releasing a reviewed run
is now a per-publish Kubernetes Job — a second queue beside the run queue, drained
by the [dispatcher](/components/dispatcher/overview/) into a new `tcab-publisher`
binary — and the console ships as a pod served wherever the backend runs. With the
last off-cluster pieces gone, **`azure-prod` comes online as a real,
VPN-reachable production environment**: its own subdomain with automatic TLS, all
secrets sourced from Azure Key Vault, and a self-healing catalog.

The other through-line is making the pipeline survive contact with a busy, real
cluster — a run that is merely waiting for capacity no longer counts as a failure,
a severed exec stream no longer fails an otherwise-complete run, and a force
re-ingest no longer 404s the versions it is rebuilding.

This remains pre-1.0 software, built first for the people working on the project.

## Breaking changes

### The standalone "push" run operation is gone

The run lifecycle drops from three operator steps to two: **review → publish**.
"Push" was a vestige of the long-lived-worker model — an explicit step that
released a finished run and stored its record *before* review. In the in-cluster
ephemeral-pod model there is nothing for it to do: when the
[driver](/components/driver/overview/) finishes a run it reports the produced
[record](/components/core/run-records/) to the backend automatically (stored
**privately**) and uploads the run tree to the
[artifact service](/components/artifacts/overview/), where the build is
**playable for review** immediately. By [v0.3.1](/changelogs/v0.3.1/) every push
surface had already been reduced to a no-op; v0.3.3 removes the dead surface
end to end:

- **The `tcab push` subcommand is removed** from the [CLI](/components/cli/overview/),
  along with the "Push run" button in both consoles. Review and publish no longer
  gate on a prior push.
- **The backend's `POST /runs` push route is removed** (the storage primitive the
  driver uses to record a finished run stays). The core's `Publisher::push`
  family, `BackendClient::push_run`, and the `PushRequest`/`PushResponse` wire
  types and their generated contract schema are gone; the release input type is
  renamed `PushRequest` → `ReleaseRequest`.
- **The docs now describe a run as "stored when produced"** rather than pushed —
  see [results](/components/core/results/),
  [terminology](/terminology/), and
  [architecture](/components/architecture/). `tcab publish` remains a solo
  convenience that self-reviews and publishes in one shot.

The arena's separate "pushed-run controller" concept is unrelated and unchanged.

## Features

### Publishing is an asynchronous, in-cluster Job

`POST /runs/{id}/publish` no longer flips a run public synchronously on the
backend. It now **gates and enqueues**: it checks the run is a completed,
non-infrastructure-failure run carrying at least one review, inserts a
`publish_job` row (`queued`) with a per-job token, and returns **`202 Accepted`**
with a `/publish-jobs/{id}/live` URL. From there the release runs entirely in the
cluster, mirroring how a run executes:

1. The **dispatcher** drains the publish queue each tick (after the run queue),
   claiming a job over a service-token route and flipping it `queued` →
   `dispatched` atomically.
2. It builds **one minimal `tcab-publisher` Job** per claim — no sandbox
   passthrough, no subscription volume, no ServiceAccount (the publisher is
   HTTP-only and never creates pods), just the backend/artifacts URLs and the
   GitHub + Cloudflare release secrets.
3. The publisher pod — which has no local checkout — **downloads the run's source
   tree** from the artifact service's new `GET /runs/{id}/tree.tar` (an
   `application/x-tar` of `implementation/` plus the record and event log, the one
   token-gated read on that service), performs the GitHub-repo creation and
   `wrangler pages deploy`, and **streams progress lines** back to the backend.
4. On success the backend patches the run's links, flips it `published`, and
   regenerates the public snapshot/gallery; on failure it records the reason. The
   terminal item closes every live subscriber's stream.

`tcab publish` and the console both **consume that live stream** instead of
blocking on a synchronous call — each progress line is printed/rendered as it
arrives, and a run is only marked published when the stream reports success. The
new `tcab-publisher` crate (`crates/publisher/`) builds to its own GHCR image that
deliberately drops the driver image's Playwright/Chromium layer (it renders
nothing). See [results](/components/core/results/),
[dispatcher](/components/dispatcher/overview/), and
[artifacts](/components/artifacts/overview/).

### `azure-prod` is a reachable production environment

Several pieces land together to make the Azure prod overlay a real environment a
VPN client can reach and an operator can keep running:

- **A private, never-public ingress.** A reusable `internal-ingress` component
  exposes the console and the four backend services over a **VPN-only internal
  load balancer** under a dedicated **`tcab.testcabinet.ai`** subdomain
  (`console`/`api`/`auth`/`artifacts`/`arena`), with TLS issued automatically by
  cert-manager via a Let's Encrypt **DNS-01** challenge through Cloudflare. The
  subdomain keeps the Azure Private DNS zone from shadowing the public
  `testcabinet.ai` gallery and docs; only the A records are private, and the
  backend's server-side auth URL deliberately stays in-cluster.
- **All secrets from Azure Key Vault.** A `keyvault-csi` component mirrors vault
  secrets into the native Kubernetes Secrets the services consume, authenticated
  by Azure Workload Identity, so nothing sensitive is committed. A small always-on
  pause Deployment mounts the provider so the CSI driver keeps the synced Secrets
  fresh; `scripts/enable-secret-rotation.sh` turns on add-on auto-rotation so a
  changed vault value reconciles on its own (~2 min) — which matters because the
  harness subscription tokens (Claude Code's expires ~daily) are now uploaded to
  the vault by `scripts/upload-subscription-creds.sh` and mounted read-only into
  each driver Job.
- **A self-healing catalog.** Because the managed-Postgres overlay gives the
  backend an ephemeral def store, catalog ingest runs as a **one-shot sidecar in
  the backend pod** that clones the repo and POSTs `/ingest` over localhost on
  start (sidestepping the default-deny NetworkPolicy). Catalog changes are then
  published **on demand** with `scripts/reingest-prod.sh`, which drives the
  cluster via `az aks command invoke` — no local kubeconfig needed.

A NetworkPolicy fix also lets the backend reach `tcab-auth` (see Fixes), without
which run creation 502'd. See [deployment](/deployment/overview/).

### The web console ships in-cluster everywhere

`apps/web` is now packaged as a static **nginx image** (`tcab-web`) configured at
**runtime** — an entrypoint renders `/config.js` from `TCAB_WEB_BACKEND_URL` /
`TCAB_WEB_AUTH_URL`, so one environment-agnostic image per git-sha is pointed at
each environment by env var rather than baked at build time. A reusable
`components/web` Deployment+Service is nested into both the local and prod
overlays. Locally, `make local-up` now brings the **entire UI** up in the cluster
and forwards it on `127.0.0.1:1430` — there is no separate `npm run dev` and no
`VITE_BACKEND_URL`/`.env.local` to set. See [Running](/development/running/).

### Run-container images are pinnable by git-sha and multi-arch

The five run-container images are now published **multi-arch**
(`linux/amd64` + `linux/arm64`, each built on a native runner and fused into a
manifest list) — the deployments run on arm64 nodes, where an amd64-only image
made every run pod die with `exec format error`. CI now also tags an immutable
`:<git-sha>` manifest list beside `:latest`. Run-container images aren't
Kubernetes `image:` fields (the driver resolves them at runtime), so the
**dispatcher now forwards** `TCAB_CONTAINER_TAG` and the per-image overrides into
every driver Job, making a cluster pin or roll back its run images on the same
staging → prod sha flow as the service images. A new
[guide](/guides/rolling-prod-service-images/) documents the rollout.

### Catalog ingest is atomic

A force re-ingest used to rebuild a version **in place** — deleting the version
dir, then copying, rendering references, and writing the manifest last — leaving
it manifest-less for the seconds-to-minutes the reference mockups take to render,
so any run resolving that version mid-re-ingest got a `404 "is not ingested"`.
Each version is now built in a staging dir and **swapped into place with a
rename**, so a concurrent resolve always sees either the old or the new version,
never a half-built tree. This is what makes the on-demand prod reingest safe to
run while runs execute.

### The run review UI is rebuilt around individual reviews

A run's individual reviews are now first-class, linkable surfaces instead of being
collapsed into one aggregate verdict. The Verdict tab still shows the aggregate
[verdict](/components/core/results/), but beneath it a new **review list** shows
each review as a compact, clickable card — reviewer and overall rating, then
timestamp and score, over a clamped writeup excerpt — and each opens its **own
page** at `/runs/:runId/reviews/:reviewerId`. The Edit control moves onto a
reviewer's own review page, the "Reviewing as…" notice shows only while a review
is actually open, and a checklist item's note renders on its own line.

### Local development runs inside the devcontainer

The devcontainer and the local `Makefile` now run the whole local stack **inside
the devcontainer** against the host Docker daemon (Docker-outside-of-Docker): the
host runtime socket is bind-mounted in, a pinned client-only Docker CLI plus `k3d`
and `kubectl` are installed by setup scripts, and socket permissions are aligned
automatically so `DOCKER_GID` need not be matched by hand. Every cluster-operating
recipe is now pinned to the k3d context, so an `apply` or `restart` (or a secret)
can no longer silently target a staging/prod cluster that happens to be the active
context.

## Fixes

### Runs queue for capacity instead of failing

When the cluster had no free capacity, a sandbox pod sat `Pending` and the driver
failed the run after a single 180s deadline — reporting a healthy run that was
merely waiting its turn as an infrastructure failure. The pod wait is now two
phases: a **scheduling** wait (until the pod is bound to a node) bounded only by an
opt-in `TCAB_K8S_POD_SCHEDULE_TIMEOUT_SECONDS` that defaults to waiting forever, so
a busy cluster makes runs queue; and the existing tight **startup** timeout once
scheduled, so a genuinely broken pod still fails fast. Time spent queued for
capacity is subtracted from the run's recorded duration. See
[Kubernetes](/deployment/kubernetes/).

### Run-artifact collection survives a torn exec channel

The driver collects a finished run's tree by streaming `tar -c /work` over the
kube exec WebSocket and reading the exit code from the channel's terminating
`Status` frame. When a managed API-server tunnel severed that long-lived stream, no
`Status` arrived, so the exit came back as `-1` with empty stderr even though the
run had finished and its tree was intact — and because the dispatcher never retries
a driver Job, a single transport blip permanently failed an otherwise-complete run.
Collection (a read-only `tar`) is now retried up to four times with exponential
backoff, treating a torn channel as retryable.

### Publishing reliability

The new publish path hit several real-world failures, now handled:

- **GitHub post-create permission lag.** `gh repo create --push` fired the push
  ~1s after creating the repo, before the creator's write grant propagated to the
  git backend, failing with `403 Permission denied` — and the empty repo it left
  behind then made every re-publish skip the push, stranding the run. Repo
  creation and the push are now separate steps, the push retries with backoff
  (~18s), and `release_code` is idempotent so a re-publish recovers a repo whose
  first push never landed.
- **Opaque deploy failures.** A failed `wrangler pages deploy` rendered as
  "command failed:" with nothing after it, because the shared error helper read
  only stderr while wrangler writes its diagnostics to stdout. Failures now draw
  from both streams.
- **Cloudflare account discovery.** `wrangler` couldn't auto-discover the account
  from a Pages-scoped token; the publish Job now provides `CLOUDFLARE_ACCOUNT_ID`
  so it skips discovery.

### The backend can reach the auth service

The base NetworkPolicy admitted the auth service from the dispatcher, driver,
artifacts, and arena — but not from the backend itself, which verifies every
bearer token in-cluster. Under default-deny ingress on an enforcing CNI that
verify call timed out and **run creation failed with a 502**. The policy now
includes the backend as an allowed source.

### Deleting a run cleans up its queue rows

`delete_run` removed the run and its cascading reviews and links but left the
run-queue and publish-queue rows behind — both reference the run by a plain column
with no foreign key, so nothing cascaded. Both queue rows are now deleted in the
same transaction.

### Console polish

- The run-detail pages no longer crash on the **static public gallery**
  (testcabinet.ai): `RunDeleteControl` read the worker context above its own guard,
  throwing where no `WorkersProvider` is mounted; it is now gated at its mount
  site, mirroring how the gallery already gates its other worker-reading controls.
- Review cards no longer carry the global hover underline (only their border
  shifts), and the gap above the first review is widened.
- The active tab label regains its dark readability halo (the accent glow alone had
  no contrast over the warm background), and the run-detail failure banner is fully
  opaque over the animated backdrop.
- The orange glow is dropped from run-table case titles (it read as a stray
  background), and the console tabs now show the cabinet favicon.
