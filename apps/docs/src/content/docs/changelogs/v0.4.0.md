The [asset-generation](/testing/asset-generation/overview/) test type learns a
third dimension. Alongside the 2D `sprite` and `sprite-sheet` kinds, a case can now
ask a model to build a **3D voxel asset** — either a static `voxel-model` or a
rigged, animated `voxel-animation` — through the same regenerate-from-actions
design that makes the 2D kinds tamper-proof. A voxel run's authoritative output is
still its recorded operation log; the validator regenerates the voxel data and an
isometric preview from it, and the console renders an **interactive 3D model**.

The headline of the animated kind is the **rig**: a `voxel-animation` is not a
fixed animation but a posable model — named parts in a hierarchy with named joints
a consuming game drives at runtime ("rotate the turret to 37°"). A new
`@test-cabinet/voxel-runtime` package poses a produced rig for both the review
viewer and real games.

This remains pre-1.0 software, built first for the people working on the project.

## Features

### Two new asset-generation kinds: `voxel-model` and `voxel-animation`

A case declares one of two new `asset_kind`s to produce a 3D asset instead of a 2D
image (see [Manifests](/testing/asset-generation/manifests/#voxel-cases)):

- **`voxel-model`** — a static opaque-RGB voxel model, sculpted with the new
  **`voxel`** binary.
- **`voxel-animation`** — a rigged, animated model, sculpted per part with the new
  **`voxel-anim`** binary (a required `--part <name>` on every op) plus rig
  subcommands.

Both replace the `[canvas]` table with a `[voxel]` table (`width`/`height`/`depth`
and a preview `background`); the volume is **opaque `#rrggbb`** with no alpha and
starts **empty**. The binaries live in the new `crates/voxel` crate and share one
voxel-and-raster library with the validator — including a **fixed, integer-only
isometric rasterizer** that serves both the in-container preview and the post-run
regeneration, so [cheat-divergence](/testing/asset-generation/evaluation/#cheat-detection)
is as enforceable in 3D as it is for a sprite. Each kind runs in its own
run-container image (`test-cabinet-voxel`, `test-cabinet-voxel-animation`), pinnable
by the `TCAB_CONTAINER_IMAGE_VOXEL` / `TCAB_CONTAINER_IMAGE_VOXEL_ANIMATION`
overrides (see [Execution](/components/core/execution/#containerization)). See
[The voxel binaries](/testing/asset-generation/voxel-binaries/).

### The rig: parts and joints a game can pose

A `voxel-animation` case's `[model]` table declares a **rig** — a required set of
`[[model.part]]` entries (a parent/child hierarchy, each with an attachment pivot)
and `[[model.joint]]` degrees of freedom (rotations or translations with a
`min`/`max`/`rest` range). Each joint is either **caller-driven** (a consuming game
supplies its value at runtime — the stable, game-facing control such as
`turret_yaw`) or **auto-play** (the model defines a looping keyframe clip). The
manifest fixes the **required** interface and the scoring targets; at run time the
model may **add** further parts, joints, and clips, and the produced `rig.json`
carries everything. The validator reconciles the produced rig against the required
one — a missing required joint is a recorded, zero-scored contract gap, not a crash.
See [Voxel models and rigs](/testing/asset-generation/overview/#the-rig-parts-and-joints)
and [Evaluation](/testing/asset-generation/evaluation/#voxel-regeneration).

### `@test-cabinet/voxel-runtime` renders and poses a produced rig

A new package (`packages/voxel-runtime`) turns a run's `rig.json` and per-part
`voxels.json` into a posable, renderable 3D model. It splits into a **pure core**
(framework-agnostic posing math — `poseRig(rig, { caller, time })` — with no
rendering dependency) and a **three binding** (mesh building plus a `VoxelRig` scene
object, with `three` as a peer dependency). It is consumed by both the in-repo 3D
viewer and real games that embed a produced model, so the posing math lives in one
place. See [voxel-runtime](/components/voxel-runtime/overview/).

### The console renders voxel runs in 3D

The [UI library](/components/ui/overview/) gains a lazy-loaded `VoxelViewer` — a
React Three Fiber canvas mounting the runtime's `VoxelRig`. A `voxel-model`
**auto-rotates**; a `voxel-animation` gives one **orbit-drag** viewer per animation
with a range control per caller joint (the `turret_yaw` slider) and playback of each
auto-play joint. Where WebGL is unavailable or reduced motion is requested it falls
back to the regenerated isometric preview PNG, so a run stays reviewable. A
voxel-animation `[[review_item]]` can name the caller joints it is about, so the
review UI surfaces exactly that joint's control beside the item.

### New authoring skills and docs

Four new [skills](/) — `authoring-a-voxel-model-test-case`,
`authoring-a-voxel-animation-test-case`, `adding-a-voxel-model-variant`, and
`adding-a-voxel-animation-variant` — mirror the sprite/sprite-sheet skills adapted
to 3D. The asset-generation docs cover the new kinds throughout
([overview](/testing/asset-generation/overview/),
[manifests](/testing/asset-generation/manifests/),
[the voxel binaries](/testing/asset-generation/voxel-binaries/), and
[evaluation](/testing/asset-generation/evaluation/)).
