v0.4.0 introduces a new **test type** — performance — and its first case,
**Lattice**. Where the [adversarial](/testing/adversarial/overview/) type added in
v0.2.0 pits a model's wasm against other models', the performance type runs a
single solution against a fixed problem and scores it on **how little work it
does** — measured in wasmtime's deterministic [fuel](/testing/performance/overview/),
so the number is reproducible across machines.

This is still pre-1.0 software intended primarily for project developers.

## Features

### The performance test type

A [performance](/testing/performance/overview/) case fixes a problem and a
contract, builds the model's solution to a wasm module, and scores it in two steps,
in order: [**correctness first, then fuel**](/testing/performance/evaluation/). A
fast wrong answer is no answer at all, so a solution earns a fuel result only once
it is known correct; between two correct solutions, the one that consumed less fuel
is the better engineering. The manifest gains a `[contract]` (`entry` plus
`input`/`output` schemas), a per-scenario `[sandbox]` (`fuel_limit` +
`max_memory_bytes`), and a `[[case]]` set pairing each held-out input with the
answer a correct solution must produce. See
[Manifests](/testing/performance/manifests/).

`core` gains a `PerformanceValidator` that reuses the shared wasm host to run a
submission once per scored case and gate on correctness, recording the consumed
fuel as the result.

### Lattice — the first performance case

[**Lattice**](/testing/performance/performance-factorio/overview/) (on-disk slug
`performance-factorio`) asks a model to write a **deterministic Factorio-style
factory-simulation engine** — two-lane belts with item compaction, splitters,
inserters, assemblers, and the source/sink fixtures that feed and drain them — and
scores it on how little fuel it spends reproducing a reference engine's exact,
bit-for-bit output. Everything is integer / fixed-point, so the state after *N*
ticks is a single value every correct engine must agree on; correctness is checked
by [**checksum**](/testing/performance/performance-factorio/architecture/#determinism-and-the-canonical-state)
at each snapshot, Factorio's own desync-detection model.

The case ships its authoritative engine and tooling as new crates under
`crates/`: `lattice-core` (the oracle — rules, fixed-point world, canonical state +
checksum; compiles natively *and* to `wasm32-unknown-unknown`), `lattice-host` (the
reusable wasmtime host the CLI and validator share), `lattice-cli` (the `lattice`
binary: `solve`/`run`/`gen`/`schema`), `lattice-sdk` (the guest ABI glue), and two
reference engines — `lattice-ref-naive` (the move-every-item floor) and
`lattice-ref-transport` (the efficient baseline). Both post identical checksums; the
transport engine does so for a fraction of the fuel, which is the whole point of the
case. A new `test-cabinet-performance` run-container image bakes the `lattice` CLI,
the engine buildkit, the reference engines, and the training scenarios; the held-out
scored set is committed with the case and never reaches the image.

The browser-replay renderer that visualizes a factory run is a **planned
enhancement**, not part of v1 — a performance run's decisive signal is correctness
plus the fuel number.
