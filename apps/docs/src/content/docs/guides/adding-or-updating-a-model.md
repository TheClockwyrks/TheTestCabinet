title: Adding or Updating a Model
---

The model catalog is the list of subjects a run can be attributed to — the
Anthropic, OpenAI, Google, and other models the suite drives through a
[harness](/components/core/harnesses/). This guide covers adding a new model and
refreshing the ones already there. If you just need the commands, the
[Add or Update a Model](/quickstarts/add-or-update-a-model/) quickstart is faster.

## What a model is on disk

Each model is two files under
[`models/`](https://github.com/TheClockwyrks/TheTestCabinet/tree/master/models):

- **`<slug>.toml`** — the catalog declaration. It is exactly five fields:
  `name`, `provider`, `openrouter_slug`, `description` (the `.md` filename), and
  `model_ids`. Notably **absent** are price, context window, and release date —
  those are looked up live from OpenRouter at catalog-build time, so the
  declaration never goes stale.
- **`<slug>.md`** — the site-facing prose shown on the model's page. This is
  written **by hand**; the scaffolder only drops a clearly-marked placeholder
  when none exists, and never overwrites real prose.

The `<slug>` is the file stem (e.g. `claude-sonnet-5`). By convention it matches
the id a harness reports for the model, so it lines up with run records.

These files feed one generated artifact: **`packages/ui/src/app/data/models.json`**,
the bundled dataset every host (the static site, the desktop and web consoles)
ships so model metadata and prices render without a backend round-trip. It is
committed to the repo and regenerated by `tcab catalog`.

## Prerequisites

- A source checkout with a working Node and Rust toolchain — see
  [Building](/development/building/).
- The model's **OpenRouter slug**, and confirmation the model is actually listed
  on OpenRouter. `tcab catalog` resolves prices, context window, and release date
  from OpenRouter's `/models` listing; a model that isn't there still works, but
  those fields land as `null`.

## Adding a new model

### 1. Scaffold the two files

`scripts/add-model.mjs` derives everything it can from OpenRouter's listing:

```sh
node scripts/add-model.mjs <openrouter-slug> [output-slug]
```

- `<openrouter-slug>` is the id OpenRouter lists the model under, e.g.
  `anthropic/claude-sonnet-5` or `openrouter/pareto-code`.
- `[output-slug]` is the optional file stem. It defaults to the part after the
  `/`, but pass an explicit value when a harness's own id convention differs —
  for Anthropic and OpenAI it should match the native id (e.g. `claude-sonnet-5`).

The script writes `models/<slug>.toml` and, only if it does not already exist,
a placeholder `models/<slug>.md`. It is safe to re-run.

> **Generating several at once?** Point `TCAB_OR_MODELS_CACHE` at a saved copy of
> the OpenRouter `/models` JSON to skip the network fetch on each invocation.

### 2. Understand the generated `model_ids`

`model_ids` is the one field worth understanding, because it is what maps a run
record's `subject.modelId` back to this catalog entry. Different harnesses report
a model under different ids, so the list carries every form:

- **Most harnesses** route through OpenRouter and report the slug unchanged, so
  the OpenRouter slug is always listed.
- **OpenCode and Kilo Code** also route through OpenRouter but prefix the slug
  with their own `openrouter/` provider id — so every entry additionally lists
  `openrouter/<slug>`.
- **Anthropic and OpenAI** are the exceptions: they run through Claude Code and
  Codex, which report a **provider-native** id. For those, the entry also lists
  the native id — for Anthropic, the slug tail with version dots rewritten to
  dashes (`anthropic/claude-sonnet-5` → `claude-sonnet-5`).

The scaffolder produces the right list for the provider automatically. Only edit
it if a harness you care about reports something not covered. See
[Harnesses](/components/core/harnesses/) for the reporting details.

### 3. Write the description

Replace the placeholder `models/<slug>.md` with real, site-facing prose. Match
the house style of the existing entries — `claude-sonnet-4-6.md` and
`gpt-5.4-mini.md` are good models: a lead sentence placing the model, then a
paragraph on what its runs tell you about the suite, closing on the OpenRouter
pricing note.

### 4. Regenerate the bundled dataset

```sh
cargo run -p test-cabinet-cli -- catalog
```

(Or `tcab catalog` from a release build.) This reads every `models/<slug>.toml`,
inlines its `.md`, looks up each model's OpenRouter prices, context window, and
release date, and writes `packages/ui/src/app/data/models.json`. It needs **no
API keys** and stays runnable offline — a failed lookup degrades that model's
prices to `null` rather than failing the build.

### 5. Verify and commit

```sh
node -e 'console.log(require("./packages/ui/src/app/data/models.json").find(m => m.slug === "<slug>"))'
```

Confirm the entry has resolved `prices`, a `contextLength`, and a `releasedAt`.
Then commit **both** the `models/` files and the regenerated `models.json`:

```sh
git add models/<slug>.toml models/<slug>.md packages/ui/src/app/data/models.json
```

The site build is pure Node with no Rust step, so it ships whatever `models.json`
is committed — an un-regenerated dataset is the most common mistake.

## Updating existing models

Because prices, context windows, and release dates are resolved live, keeping the
catalog current is just re-running the build:

```sh
cargo run -p test-cabinet-cli -- catalog
git add models/ packages/ui/src/app/data/models.json
```

This is exactly what a scheduled job (or a release step — see
[Releasing](/development/releasing/)) does to keep the committed prices fresh. To
change a model's **name, provider, OpenRouter slug, or prose**, edit its `.toml`
or `.md` by hand first, then re-run `tcab catalog`.
