# v0.36.0

## What the update brings

A push hook that refuses a push whose commits pin a submodule commit the
submodule's remote lacks, which no other checkout and no pipeline could check
out.

- `ci/gates/submodule-remotes.py`, a gate run as the pre-push hook. For each
  commit the push would publish, it takes every submodule pin that commit
  moved, lists the branches and tags of the remote that commit's
  `.gitmodules` names for the submodule and, where none stands at the pin,
  fetches the ones it lacks into the submodule's repository, writing no ref,
  and fails the push naming each pin no branch or tag holds, the remote and
  the commits pinning it. It recurses into the pinned commit's own
  submodules, uses the developer's own credentials, refuses an address that
  opens with `-`, passes at once in a repository with no `.gitmodules`, and
  passes outside a push, saying nothing is being pushed.
  `ci/tests/test_submodule_remotes.py` drives it against local repositories.
- `git()` in the `ci` library takes `stdin`, written to git's standard input,
  for the commands that read a list there.
- `.pre-commit-config.yaml` names `default_install_hook_types: [pre-commit,
  pre-push]` and `default_stages: [pre-commit]`, pins the upstream hooks whose
  own manifests also name the push stage (`check-added-large-files`,
  `check-executables-have-shebangs`, `end-of-file-fixer` and
  `check-shebang-scripts-are-executable`) to `stages: [pre-commit]`, and adds
  the `submodule-remotes` hook at `stages: [pre-push]`. Every other hook runs
  at the commit, as before.
- `scripts/setup-hooks.sh` installs the push hook beside the commit hook.
- `ci/tests/test_wiring.py` names the push gates in `PUSH_GATES`, holds their
  hooks to the push stage and every other hook to the commit stage, and holds
  the pipeline to giving them no step, since it runs on commits already pushed.
- `CLAUDE.md`, `ci/README.md` and the documentation's building page name the
  gate.

## Questions

It adds no question and stops asking none, so every recorded answer stays as it
is.

## Steps by hand

- A project that added a hook of its own to `.pre-commit-config.yaml` from an
  upstream repository whose manifest names the push stage gives it
  `stages: [pre-commit]`, or the wiring tests name it.
- A project that removed a gate from the pipeline's steps or added one keeps
  `submodule-remotes` out of `azure-pipelines.yml`, which the wiring tests hold.
- Run `scripts/setup-hooks.sh` once in every clone, on every machine, so the
  push hook is installed there. A devcontainer created after the update runs it
  itself.
