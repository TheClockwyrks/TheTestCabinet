# v0.40.0

## What the update brings

The push hook admits a submodule pin only from a branch of the submodule's
remote that a landing of the pushed branch can target, so a pin that only a tag
or another worktree's branch holds is refused at the push rather than stopping
the landing later.

- `ci/gates/submodule-remotes.py`, for a push to the branch `<b>`, admits a pin
  the push publishes when the submodule remote's branch `<b>` holds it, or when
  a branch of that remote holds it whose name is no managed worktree branch's,
  `issue/*`, `task/*` or `filing/*`. A tag alone no longer admits a pin, and
  neither does an `issue/*`, `task/*` or `filing/*` branch other than `<b>`. A
  push that updates no branch, or a range checked by hand, is held to the
  branches that are no worktree's alone. It lists the remote's branches alone
  and fetches only the ones it considers, and a refused pin is named with the
  remote, the commits pinning it and the branches it was looked for on.
- `ci/tests/test_submodule_remotes.py` holds a pin only a tag holds, or only an
  `issue/`, `task/` or `filing/` branch other than the pushed one, to failing,
  and a pin the pushed branch's namesake holds to passing.
- The hook's description in `.pre-commit-config.yaml`, the gate list in
  `CLAUDE.md` and the documentation's building page state the new rule.

## Steps by hand

- Run `scripts/setup-hooks.sh` once in every clone, on every machine, so the
  push hook is installed there. The hook is what applies the rule, and a clone
  made before `v0.36.0`, or whose hooks were installed with a bare
  `pre-commit install`, carries no `pre-push` hook at all: a checkout holding
  submodules was found with none until the script was run in it, so its
  pushes had never been checked. The script is idempotent, so running it in a clone
  that has the hook changes nothing.
- A submodule pin already published that only a tag or another worktree's
  branch holds is not judged again, since the gate checks only the commits a
  push publishes; merge such a commit to the submodule's branch the landing
  targets, such as `master`, before the next landing of the repository pinning
  it.
