## What the update brings

The template publishes ten language images, each holding one toolchain a
project builds WebAssembly components with, and the devcontainer copies each
one the project answers yes to.

- `.devcontainer/ubuntu.dockerfile` names each language image the project
  answers yes to as a stage, copies it over the toolchain image after the
  browser engines, and publishes the environment naming where it sits. The
  `x-devcontainer-build-args` anchor of `.devcontainer/docker-compose.yml`
  names each such image by full reference, as `<NAME>_IMAGE`.
- The images and what the Dockerfile publishes for each:
  - `wasm-components`: wasmtime, wit-bindgen, wasm-tools, wac and the WASI
    preview 1 command adapter, whose path is
    `WASI_PREVIEW1_COMMAND_ADAPTER`.
  - `rust-nightly`: the dated nightly channel with its `wasm32-wasip2`
    target, which `cargo +nightly` runs.
  - `wasi-sdk`: the WASI SDK, whose prefix is `WASI_SDK_PATH`.
  - `python`: a pinned CPython, whose directory `PYTHON_BIN_DIR` leads the
    `PATH`, and componentize-py.
  - `jvm`: the JDK, as `JAVA_HOME`, Kotlin, Gradle, and its seeded cache, as
    `GRADLE_USER_HOME`.
  - `dotnet`: the .NET SDK, as `DOTNET_ROOT`, and its local package feed, as
    `DOTNET_LOCAL_FEED`.
  - `ruby`: the ruby.wasm builder and YARD in `GEM_HOME`, and binaryen.
  - `swift`: the Swift toolchain and its SDK for WebAssembly.
  - `purescript`: the PureScript compiler and spago.
  - `ecmascript`: TypeScript, typedoc and jco.
- The toolchain image moves for every project. The base image it is built on
  installs the system half the toolchains link against, such as clang, cmake,
  Ruby and the libraries the Swift and .NET toolchains load, and its stable
  Rust toolchain gains the `wasm32-unknown-unknown`, `wasm32-wasip1` and
  `wasm32-wasip2` targets. `TOOLCHAIN_IMAGE` names the new tag, and the CI
  images under `ci/images/`, built on it, move with it.
- `.devcontainer/README.md` describes each toolchain the project carries
  under "The language toolchains".
- `ci/images/web.Dockerfile` puts `/home/dev/.cargo/bin` on its `PATH`, so a
  web job that compiles Rust, such as a WebAssembly build the web gates read,
  links with the mold driver the toolchain image names as every glibc
  target's linker.

## Questions

It adds ten questions, each asking whether the devcontainer carries one
toolchain and each defaulting to no: `toolchain_wasm_components`,
`toolchain_rust_nightly`, `toolchain_wasi_sdk`, `toolchain_python`,
`toolchain_jvm`, `toolchain_dotnet`, `toolchain_ruby`, `toolchain_swift`,
`toolchain_purescript` and `toolchain_ecmascript`. An update run with
`--defaults` answers each with its default, so an existing workspace carries
none of them and renders what it did beside the moved images. It stops asking
none, so every recorded answer stays as it is.

To carry a toolchain, answer its question on the update, either with
`--data`:

```sh
copier update --trust --conflict inline --data toolchain_swift=true
```

or by running `copier update --trust --conflict inline` without `--defaults`
and answering the questions as copier asks them. The answers are recorded, so
a later update keeps them. A project building components in any language
answers yes to `toolchain_wasm_components` as well. The language images'
references and versions come from answers the template never asks and copier
never records, so each update renders the new version's.

## Steps by hand

After the update has merged:

1. A project that installed one of these toolchains in a step of its own
   `ubuntu.dockerfile` removes that step and the scripts it ran, and answers
   the toolchain's question instead. Its own pins of that toolchain move to
   the versions the template pins, which the image's tag names, and anything
   that read such a version out of the compose file's anchor reads it from
   the tag of the image's `<NAME>_IMAGE` entry instead.
2. On each machine, rebuild the devcontainer image once, with **Rebuild
   Container** in the editor or `devcontainer up --remove-existing-container`.
   The base and toolchain images moved, so the rebuild pulls them, with each
   language image the project answered yes to.
3. Once the image pipeline has built the CI images on the commit holding the
   update, write that commit into `ci/images/tags.yml` as `ciImageTag` in a
   second commit, as `ci/images/README.md` describes.
