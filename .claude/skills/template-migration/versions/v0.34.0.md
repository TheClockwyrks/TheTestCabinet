## What the update brings

The devcontainer image and the CI images are built on the images the template
publishes to `nyxsisdev.azurecr.io`, a registry that admits anonymous pulls.

- `.devcontainer/ubuntu.dockerfile` is built `FROM` the published toolchain
  image, which holds the system packages, the account and every language and
  tool a workspace carries. It copies the tool images the project's shape
  carries over it: the Android toolchain on amd64, with an empty stage in its
  place on arm64, the Tauri CLI, and the browser engines. It then runs only
  CUDA, the project's own steps at the comment marking their place, the Codex
  and Claude Code CLIs and `post-install.sh`, each step declaring only the
  build arguments it reads.
- The `x-devcontainer-build-args` anchor of `.devcontainer/docker-compose.yml`
  names the published images by full reference, `TOOLCHAIN_IMAGE`,
  `PLAYWRIGHT_IMAGE` and, where the project builds them, `TAURI_IMAGE` and
  `ANDROID_IMAGE`, beside `INSTALL_CUDA`, `CODEX_VERSION` and
  `CLAUDE_CODE_VERSION`. Every other pin, `USERNAME`, `USER_UID`, `USER_GID`
  and `INSTALL_ANDROID` leave it. A later template version moves the image
  references, so updating the template is what moves the workspace onto new
  images.
- The container's account is the published image's `dev` at uid and gid 1000
  on every machine. `.env.podman` and `.env.macos` state no
  `DEVCONTAINER_UID` or `DEVCONTAINER_GID`, and map the host's account onto the
  image's with `DEVCONTAINER_USERNS=keep-id:uid=1000,gid=1000`, whatever ids
  the host's account has.
- The CI images under `ci/images/` are built `FROM` the same toolchain image
  and install nothing; each `.dockerignore` excludes the whole context.
- The render stops carrying the install scripts only a published image runs:
  `.devcontainer/system/apt.sh`, `system-config.sh`, `init-user.sh`,
  `browser-deps.sh`, everything under `.devcontainer/languages/`,
  `ai/claude-managed-settings.json`, and the scripts under
  `.devcontainer/tools/` that installed a tool, leaving the ones a container
  runs at start.

## Questions

It adds no question and stops asking none, so every recorded answer stays as it
is. The image references come from answers the template never asks and copier
never records, so each update renders the new version's.

## Steps by hand

Before updating, on each machine the workspace is built on:

1. Confirm the machine's container runtime can pull from
   `nyxsisdev.azurecr.io` with no login, for example with
   `podman pull` of the `TOOLCHAIN_IMAGE` the new version's compose file names.

After the update has merged:

1. Move any step the project added to its own `ubuntu.dockerfile`, such as a
   database server its tests run against, to the comment the new Dockerfile
   leaves for it, above the coding-agent CLIs. The merge carries the step, and
   it may land where the old layout had it. Give it a `COPY` of only the
   scripts it runs and declare only the arguments they read immediately before
   its `RUN`, and keep those arguments in the anchor. A step that installed
   with apt runs as root, between a `USER root` and a `USER dev` line, as the
   CUDA step does. A script the project kept under a removed directory, such as
   `.devcontainer/tools/`, stays where it is.
2. Resolve the conflicts the update left in the compose file and the
   Dockerfile in favour of the new layout, keeping the project's own entries.
3. On each machine, delete the `DEVCONTAINER_UID` and `DEVCONTAINER_GID` lines
   from `.devcontainer/.env`, and set
   `DEVCONTAINER_USERNS=keep-id:uid=1000,gid=1000` there on a rootless Podman
   host, including a Mac.
4. On each machine, rebuild the devcontainer image once, with **Rebuild
   Container** in the editor or `devcontainer up --remove-existing-container`.
5. Once the image pipeline has built the CI images on the commit holding the
   update, write that commit into `ci/images/tags.yml` as `ciImageTag`, as
   `ci/images/README.md` describes.
