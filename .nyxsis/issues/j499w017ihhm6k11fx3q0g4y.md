outcome: |
  On PostgreSQL the backend now runs as two replicas that coordinate through the
  database, as the backend overview's "Replicas" section describes. That section
  was extended first.

  - **Announcements.** Every replica announces on one `LISTEN`/`NOTIFY` channel,
    and each listens on a connection of its own (`crates/backend/src/bus.rs`).
    What it announces:
    - stored event batches;
    - preview frames, whose latest frame per index is now stored in `job_preview`;
    - a job's end;
    - console stream messages;
    - topic changes forwarded to the replica that serves the stream, which
      acknowledges them;
    - publish progress and results;
    - queued snapshot refreshes;
    - ingests that refreshed the checkout.

    A payload over the notification limit goes through `relay_overflow`. When the
    listener reconnects, every stream is resynchronized. A self-ping catches a
    connection that has stopped delivering. A stopping replica sends what it has
    queued before it exits.
  - **Gaps and missed ends.** A job's stream reads back from the database any
    events it missed, found by their sequence, and closes when its job has ended,
    even if the end was never announced to it.
  - **Locks.** The snapshot refresh (which is also a publish's index rewrite), the
    reclamation sweep pass and the start's migration each hold a PostgreSQL
    session advisory lock. A caller that stops waiting for a lock releases it. A
    replica whose store is not populated runs no refresh.
  - **Shutdown.** On SIGTERM the backend fails readiness, ends its long-lived
    streams and finishes the requests in flight.
  - **Manifests.** The postgres component's `Deployment` runs 2 replicas with
    `RollingUpdate` (surge 1, unavailable 0), preferred anti-affinity, a
    `PodDisruptionBudget` of `minAvailable: 1`, a 60s grace and a `preStop` sleep.
    `/state` is on a generic ephemeral volume per pod. The deploy scripts' checks
    of the shared claim are removed.
  - **Tests.** `bus.test.rs` runs two backends over one throwaway PostgreSQL
    server. They post a batch to one backend and read it live from a subscriber of
    the other, and also cover previews, console messages, topic forwarding,
    publish items, locks, a reconnect, an unannounced batch, a cancelled lock wait
    and a refresh queued on the other replica.
  - **CI.** The devcontainer and the Rust CI image install `postgresql`, and the
    `rust` job sets `TCAB_REQUIRE_POSTGRES=1`.

  Left:

  - **CI image.** `ciImageTag` has to follow the image rebuild of
    `ci/images/rust.Dockerfile`. Until then the `rust` job's replica tests fail
    for lack of PostgreSQL.
  - **Staging drain.** A node drain on staging, checking that `GET /readyz`
    answers 200 through the Service throughout, has not been run.
  - **Launch leases.** Launch-pass leases are not renewed during a long holder,
    and `enqueue_publish_job_once` checks and then inserts. Both were seen in
    review and are not addressed here.
  - **Old claim.** The `tcab-backend-state` claim stays in each namespace and can
    be deleted by hand once the new shape has rolled out.

The backend runs as one replica with the `Recreate` strategy over a
`ReadWriteOnce` `tcab-backend-state` claim
(`deployments/k8s/components/postgres/deployment-backend.yaml`), so a node
drain takes it offline and a driver finishing a run in that window cannot
report it. Its relay and console stream fan out within one process
(`crates/backend/src/relay.rs`), and its snapshot refresher serializes in
memory (`crates/backend/src/publisher.rs`).

The documentation runs two replicas on PostgreSQL, each with its own cache
volume, coordinating through the database:

- `apps/docs/src/content/docs/components/backend/overview.md`, "Replicas"
- `apps/docs/src/content/docs/deployment/kubernetes/postgres.md`, "The
  managed-database shape"

## What is missing

- Each stored event batch and each console stream message announced through
  PostgreSQL `LISTEN`/`NOTIFY` and delivered to the subscribers of every
  replica.
- The snapshot refresh, the publish's index rewrite and the reclamation sweep
  pass each holding a database lock while they run.
- The postgres component's `Deployment` at two replicas with a rolling update,
  spread across nodes, with a `PodDisruptionBudget` of one available, and its
  `/state` on a per-pod ephemeral volume in place of the shared claim.

## Verify

- A test runs two backends over one database, posts a batch to one and reads it
  live from a subscriber of the other.
- On staging, a drain of the node holding one backend pod leaves
  `GET /readyz` answering `200` through the `Service` throughout.
- `make gate` passes in the backend checkout and the superrepo.
