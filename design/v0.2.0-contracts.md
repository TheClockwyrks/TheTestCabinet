# The Test Cabinet v0.2.0 — Integration Contracts

This is the authoritative contract every v0.2.0 component builds against. It
covers the backend HTTP API, the backend's SQLite store, the public R2 snapshot
layout, the core-side backend client trait runners call, and backend
configuration.

It is consistent with the existing run-record shape (`crates/core/src/run_record.rs`
and `packages/run-record/src/index.ts`), the review shape (`crates/core/src/review.rs`),
the test-case manifest (`crates/core/src/test_case.rs`), and the resolved v0.2.0
design decisions. Where a resolved decision conflicts with the literal spec, the
decision wins and is implemented here.

Conventions used throughout:

- All JSON is **camelCase**, matching the run-record contract.
- All timestamps are **RFC 3339** strings (matching `RunRecord.startedAt`).
- Harness slugs are the eight lowercase tokens from `HarnessSlug`
  (`claude`, `codex`, `cline`, `antigravity`, `goose`, `kilo`, `opencode`, `pi`).
- Ratings are `flawless | great | scuffed | broken`.
- There is **no app-level auth** (private network / Tailscale is the access
  control). The backend trusts every caller that can reach it.

---

## 0. Domain model recap

A **test-case version** is identified by `(slug, version)` — e.g.
`("pong", "v1.0.0")`. Its manifest (`test-case.toml`) declares variants, common
specs, common + per-variant references, validation checks, build commands, and
site-facing metadata.

A **container definition** is the build context under `containers/<harness>/`
(a `Dockerfile` plus any sibling files, e.g. `containers/base/install-playwright-browsers.mjs`).
Definitions are keyed by harness slug. There are eight harness definitions plus a
shared `base` that the others build `FROM`. The backend serves definitions; the
runner builds and caches the image locally, tagging it with a **content hash** of
the served definition.

A **published run** is a `RunRecord` + a `Writeup` (review) + resolved `RunLinks`
(source repo + playable build URL). The backend is the system of record.

### What the backend ingests vs. serves

- The backend is pointed at a **repo checkout** (`TCAB_BACKEND_CHECKOUT`). On a
  trigger/scan it reads `test-cases/` and `containers/` from that checkout and
  **copies** each version and container definition into its own store, keyed by
  slug/version (immutable once ingested). It does **not** live-serve the working
  tree.
- On ingest of a test-case version, the backend **renders each reference mockup
  (HTML) to a screenshot** (moving today's runner-side `crates/core/src/reference.rs`
  render to the backend) and stores the rendered PNGs. Runners receive **rendered
  screenshots**, never raw mockup HTML. This makes validation baselines identical
  across runners.
- Runners still need a headless browser locally for the load check + per-check
  capture; only the reference baseline rendering moves to the backend.

## 1. Backend HTTP API

Axum server. JSON request/response bodies unless noted. Errors use a single
envelope: `{ "error": { "code": <string>, "message": <string> } }` with an
appropriate HTTP status (`400`, `404`, `409`, `422`, `500`). No auth headers.

### 1.1 Health & trigger

#### `GET /healthz`
Liveness/readiness probe. No body.

```jsonc
// 200
{ "status": "ok", "version": "0.2.0", "store": "ready" }
```

#### `POST /ingest`
Trigger a scan of the configured checkout (`TCAB_BACKEND_CHECKOUT`). Ingests any
new/changed test-case versions and container definitions, renders reference
screenshots, and copies them into the store. Idempotent: an already-ingested,
unchanged `(slug, version)` or container def is a no-op. Synchronous for the
scan; returns what changed.

```jsonc
// request (all optional; default = full scan)
{
  "testCases": ["pong"],         // restrict to these case slugs (optional)
  "containers": ["claude"],      // restrict to these harness slugs (optional)
  "force": false                 // re-ingest even if unchanged (re-renders refs)
}
```

```jsonc
// 200
{
  "testCaseVersions": [
    { "slug": "pong", "version": "v1.0.0", "ingested": true, "renderedReferences": 3 }
  ],
  "containerDefinitions": [
    { "harness": "base",   "ingested": true, "contentHash": "sha256:..." },
    { "harness": "claude", "ingested": false, "contentHash": "sha256:..." }
  ]
}
```

`ingested: false` means already present and unchanged (skipped). `force: true`
sets `ingested: true` and re-renders.

### 1.2 Test-case catalog & version resolution

#### `GET /test-cases`
The catalog: every ingested case and its available versions, newest-listed-last
(insertion order). Mirrors `core::test_case::TestCase`.

```jsonc
// 200
{
  "testCases": [
    { "slug": "pong",  "versions": ["v1.0.0"] },
    { "slug": "snake", "versions": ["v1.0.0", "v1.1.0"] }
  ]
}
```

#### `GET /test-cases/{slug}/versions`
Versions for one case.

```jsonc
// 200
{ "slug": "pong", "versions": ["v1.0.0"] }
// 404 if slug unknown
```

#### `GET /test-cases/{slug}/versions/{version}`
Resolve an exact, immutable test-case version: the full manifest the runner
needs to seed and validate a run. This is `core::test_case::TestCaseVersion`
**with host-absolute paths rewritten to definition-store-relative paths** (a
runner has no checkout), plus references resolved to their **rendered
screenshot** URLs rather than mockup source paths.

```jsonc
// 200
{
  "slug": "pong",
  "version": "v1.0.0",
  "name": "Pong",
  "difficulty": "easy",
  "tags": ["arcade", "2d"],
  "summary": "A two-paddle rally game.",          // nullable
  "description": "## Pong\n…",                     // nullable; resolved description.md body (NOT seeded)
  "maxRuntimeSeconds": 1800,
  "build": { "install": "npm ci", "build": "npm run build" },
  "promptTemplate": "…handlebars source…",          // prompt.hbs contents, served inline
  "commonSpecs": [
    // source served as bytes via the artifact endpoint; `source` is a store path key, `dest` is the workspace dest
    { "source": "specs/overview.hbs", "dest": "specs/overview.md", "template": true }
  ],
  "assets": [
    { "source": "assets/ball.png", "dest": "assets/ball.png" }   // directories expanded to files
  ],
  "variants": [
    {
      "slug": "base",
      "name": "Base",
      "description": null,
      "specs": [],                                  // additive specs, same {source,dest,template} shape
      "references": [                               // additive references, resolved to rendered screenshots
        { "view": "title", "screenshotUrl": "/test-cases/pong/v1.0.0/references/base/title.png" }
      ]
    }
  ],
  "commonReferences": [
    { "view": "gameplay", "screenshotUrl": "/test-cases/pong/v1.0.0/references/_common/gameplay.png" }
  ],
  "checks": [
    {
      "view": "title",
      "name": "Title",
      "referenceView": "title",
      "actions": [ { "type": "wait", "ms": 500 } ]   // internally tagged, matches core::CheckAction
    }
  ]
}
// 404 if (slug, version) not ingested
```

Notes:
- `promptTemplate` is served inline because the runner renders it locally
  (Handlebars) — it never hits disk in the runner's checkout.
- Spec/asset **bodies** are not inlined here (a case can be large); they are
  fetched per-file from the artifact endpoint below using the `source` key.
- `references` are pre-rendered: the runner downloads the PNG and seeds it as
  the visual target and uses it as the validation baseline. The runner never
  receives mockup HTML.

#### `GET /test-cases/{slug}/versions/{version}/artifacts/{path...}`
Fetch a single seeded artifact (a spec source file or an asset file) by its
store-relative `source` key. Returns the raw bytes with an appropriate
`Content-Type` (and `Content-Length`). `.hbs` spec sources are returned verbatim
(the runner renders them). Path is validated to resolve inside the version's
store directory (no traversal).

```
200  <raw bytes>
404  if the artifact key is unknown for this version
```

#### `GET /test-cases/{slug}/versions/{version}/references/{scope}/{view}.png`
Fetch a rendered reference screenshot. `scope` is `_common` for a common
reference or a variant slug for a variant-specific one. Returns `image/png`.
(The `screenshotUrl` fields above point here.)

### 1.3 Container definition resolution

#### `GET /containers`
List the ingested container definitions and their content hashes.

```jsonc
// 200
{
  "containers": [
    { "harness": "base",   "contentHash": "sha256:9f2c…", "buildsFrom": null },
    { "harness": "claude", "contentHash": "sha256:1a7b…", "buildsFrom": "base" }
  ]
}
```

`buildsFrom` is the harness slug a definition's Dockerfile `FROM`s within the
cabinet (parsed at ingest; `null` for `base`). It lets a runner build `base`
first when required.

#### `GET /containers/{harness}`
Resolve a harness container definition: a manifest listing every file in the
build context, each with its store-relative path and a per-file content hash,
plus the aggregate `contentHash` (the hash the runner tags the built image
with).

```jsonc
// 200
{
  "harness": "claude",
  "contentHash": "sha256:1a7b…",        // hash over the whole build context (the image tag the runner uses)
  "buildsFrom": "base",                  // null for base
  "files": [
    { "path": "Dockerfile", "size": 1834, "sha256": "…" }
  ]
}
// 404 if harness unknown / not ingested
```

The aggregate `contentHash` is computed deterministically from the sorted set of
`(path, sha256)` pairs (see §4 for the exact recipe so core and backend agree).

#### `GET /containers/{harness}/files/{path...}`
Fetch one file of a container build context by its store-relative path. Raw
bytes + `Content-Type`. Traversal-guarded.

```
200  <raw bytes>
404  if unknown
```

### 1.4 Publishing a run

#### `POST /runs`
Submit a published run: the run record, the review, and the resolved links. The
operator's component (CLI/Tauri) has already released the code repo and deployed
the build before calling this; it sends the captured URLs. The backend ingests
into SQLite, then (debounced/coalesced) regenerates and uploads the R2 snapshot
and fires the site deploy hook. Idempotent on `record.id`.

```jsonc
// request
{
  "record": { /* a full RunRecord — see packages/run-record. `links` here MAY be
                  empty; the resolved links below are authoritative and the backend
                  writes them onto the stored record. */ },
  "review": {
    "rating": "great",            // flawless | great | scuffed | broken
    "writeup": "Plays well, but…"   // markdown body (frontmatter stripped)
  },
  "links": {
    "sourceRepo": "https://github.com/TheClockwyrks/tcab-pong-claude-…",
    "playableBuild": "https://abc123.test-cabinet-runs.pages.dev"  // the URL wrangler reported (NOT constructed)
  }
}
```

```jsonc
// 201 (newly published) or 200 (idempotent re-publish, record already present)
{
  "id": "9c3f…",
  "newlyPublished": true,
  "snapshotRefresh": "queued"     // queued | skipped (coalesced into a pending refresh)
}
```

Validation (`422` on failure): `review.rating` must be a valid tier; `review.writeup`
must be non-empty (publishing refuses a run without a review); `record.subject`'s
`(testCaseSlug, testCaseVersion)` should resolve to an ingested version (warning,
not hard fail, so historical cases can be re-published).

#### `GET /runs`
List stored published runs, newest first, paginated. Used by reporters (Tauri).

```jsonc
// GET /runs?limit=50&before=<rfc3339 cursor>
// 200
{
  "runs": [ { /* StoredRun: record + review + links, see below */ } ],
  "nextBefore": "2026-06-01T12:00:00Z"   // null when no more
}
```

#### `GET /runs/{id}`
One stored run.

```jsonc
// 200
{
  "record": { /* RunRecord with links populated */ },
  "review": { "rating": "great", "writeup": "…" },
  "links": { "sourceRepo": "…", "playableBuild": "…" }
}
// 404 if unknown
```

#### `POST /snapshot/refresh`
Force an immediate snapshot regeneration + R2 upload + deploy-hook fire, outside
the normal coalescing window. For operator recovery. No body.

```jsonc
// 200
{ "refreshed": true, "runCount": 128, "deployHookFired": true }
```

## 2. SQLite schema

A single embedded SQLite file (`TCAB_BACKEND_DB`), the system of record for
published runs + reviews + links. Definitions/screenshots live on disk in the
definition store (§4/§5), referenced by key — they are not stored as rows.

The full `RunRecord` is stored as one JSON column (the record's shape is the
fixed contract and is regenerated verbatim into the snapshot), with the columns
needed for ordering, pagination, and filtering lifted out for indexing. Reviews
and links are separate tables keyed by run id.

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;

-- One row per published run. `record_json` is the verbatim RunRecord
-- (camelCase JSON); the lifted columns are denormalized copies for query/sort.
CREATE TABLE run (
    id                  TEXT PRIMARY KEY,          -- RunRecord.id (UUID)
    started_at          TEXT NOT NULL,             -- RFC 3339, RunRecord.startedAt
    finished_at         TEXT NOT NULL,             -- RFC 3339, RunRecord.finishedAt
    published_at        TEXT NOT NULL,             -- RFC 3339, when POST /runs ingested it

    test_case_slug      TEXT NOT NULL,             -- subject.testCaseSlug
    test_case_version   TEXT NOT NULL,             -- subject.testCaseVersion
    variant             TEXT NOT NULL,             -- subject.variant
    harness_slug        TEXT NOT NULL,             -- subject.harnessSlug
    harness_version     TEXT,                      -- subject.harnessVersion (nullable)
    model_id            TEXT NOT NULL,             -- subject.modelId

    run_state           TEXT NOT NULL,             -- status.state: completed|failed|unevaluable
    loaded              INTEGER NOT NULL,          -- validation.loaded (0/1)

    record_json         TEXT NOT NULL              -- the full RunRecord as JSON (with links populated)
);

CREATE INDEX idx_run_published_at ON run (published_at DESC);
CREATE INDEX idx_run_case        ON run (test_case_slug, test_case_version);
CREATE INDEX idx_run_harness     ON run (harness_slug);
CREATE INDEX idx_run_model       ON run (model_id);

-- One row per run's hand-written review. 1:1 with run; required for a run to be
-- published, so the row always exists for a published run.
CREATE TABLE review (
    run_id   TEXT PRIMARY KEY REFERENCES run (id) ON DELETE CASCADE,
    rating   TEXT NOT NULL,        -- flawless|great|scuffed|broken
    writeup  TEXT NOT NULL         -- markdown body (frontmatter stripped)
);

-- One row per run's published links. 1:1 with run. Stored separately so links
-- can be re-resolved on re-publish without rewriting the record blob's siblings.
CREATE TABLE run_link (
    run_id          TEXT PRIMARY KEY REFERENCES run (id) ON DELETE CASCADE,
    source_repo     TEXT,          -- RunLinks.sourceRepo (nullable, but set on publish)
    playable_build  TEXT           -- RunLinks.playableBuild (the wrangler-reported URL)
);

-- Tracks snapshot refresh state so coalescing survives a restart. Single row.
CREATE TABLE snapshot_state (
    id              INTEGER PRIMARY KEY CHECK (id = 1),
    dirty           INTEGER NOT NULL DEFAULT 0,   -- a publish has landed since last upload
    last_uploaded   TEXT,                          -- RFC 3339 of last successful R2 upload
    last_run_count  INTEGER                        -- runs in the last uploaded snapshot
);
```

Notes:
- `record_json` is the source of truth for the snapshot: the snapshot's per-run
  record is this blob verbatim (already camelCase, links populated), so no
  reserialization drift between SQLite and R2.
- Container definitions are **not** in SQLite. They live in the on-disk
  definition store keyed by `(harness, contentHash)`; immutability is enforced by
  never overwriting an existing key. Same for test-case version artifacts and
  rendered screenshots.
- A re-publish (`POST /runs` with an existing id) updates `review`, `run_link`,
  and `record_json` (links) but keeps `published_at` from first publish.

## 3. R2 public snapshot layout

The snapshot is what the **site fetches at build time**. The backend regenerates
it from the full published set on each (coalesced) publish, uploads it to R2, and
swaps it atomically. The site keeps its existing local-runs dev plugin; the
snapshot is the production data source.

Atomic swap strategy: write everything under a content-addressed prefix
`snapshots/<snapshot-id>/…`, then write the small top-level pointer
`index.json` last (a single small object, so its overwrite is the atomic
cut-over). The site reads `index.json`, then follows it to the versioned prefix.

### Keys

```
index.json                                   # top-level pointer + summary (overwritten last)
snapshots/<snapshot-id>/runs.json            # the run index (list of summaries)
snapshots/<snapshot-id>/runs/<run-id>.json   # per-run: record + review + links
snapshots/<snapshot-id>/cases/<slug>/<version>.json  # per-case-version metadata
```

`<snapshot-id>` is a timestamp+hash (e.g. `2026-06-17T2148Z-<short-hash>`), so a
new snapshot never clobbers the previous one until `index.json` is swapped; old
prefixes can be garbage-collected after a grace period.

### `index.json`

```jsonc
{
  "schemaVersion": 1,
  "snapshotId": "2026-06-17T2148Z-1a7b",
  "generatedAt": "2026-06-17T21:48:00Z",
  "runCount": 128,
  "runsKey": "snapshots/2026-06-17T2148Z-1a7b/runs.json",
  "runsPrefix": "snapshots/2026-06-17T2148Z-1a7b/runs/",
  "casesPrefix": "snapshots/2026-06-17T2148Z-1a7b/cases/"
}
```

### `runs.json` — the index

A flat array of run **summaries**, newest first. Enough for the gallery's cards
and its client-side filter (by test case, harness, model) without fetching every
per-run file. The site fetches full records lazily per run page.

```jsonc
{
  "schemaVersion": 1,
  "runs": [
    {
      "id": "9c3f…",
      "publishedAt": "2026-06-17T21:40:00Z",
      "startedAt": "2026-06-17T20:40:00Z",
      "finishedAt": "2026-06-17T21:30:00Z",
      "subject": {
        "testCaseSlug": "pong",
        "testCaseVersion": "v1.0.0",
        "variant": "base",
        "harnessSlug": "claude",
        "harnessVersion": "1.2.3",        // nullable
        "modelId": "claude-sonnet-4-5"
      },
      "caseName": "Pong",                 // denormalized from case metadata for cards
      "metrics": {                        // RunMetrics, verbatim
        "runTimeSeconds": 3000.0,
        "tokens": { "uncachedInput": 0, "cachedInput": 0, "output": 0, "reasoning": 0 },
        "cost":   { "comparable": 0.0, "actual": 0.0 }
      },
      "validationLoaded": true,           // validation.loaded — primary signal on the card
      "state": "completed",               // status.state
      "rating": "great",                  // review rating — per-run badge, never aggregated
      "links": {
        "sourceRepo": "https://github.com/…",
        "playableBuild": "https://abc123.test-cabinet-runs.pages.dev"
      }
    }
  ]
}
```

### `runs/<run-id>.json` — per-run record + review

The full record blob (verbatim `record_json` from SQLite, links populated),
plus the review and links the site needs for the detail page (writeup gated
ahead of the embedded build, rating shown up front).

```jsonc
{
  "schemaVersion": 1,
  "record": { /* full RunRecord, camelCase, exactly the run-record contract,
                  with `links` populated */ },
  "review": { "rating": "great", "writeup": "Plays well, but the AI paddle…" },
  "links": {
    "sourceRepo": "https://github.com/…",
    "playableBuild": "https://abc123.test-cabinet-runs.pages.dev"
  }
}
```

### `cases/<slug>/<version>.json` — case metadata

The site-facing slice of a test-case version: what the gallery shows to frame a
run (name, difficulty, tags, summary/description, variant labels, declared
checks). Derived from the ingested manifest; **no** spec bodies, **no** mockup
HTML, **no** host paths. Reference screenshots are exposed as snapshot-relative
keys so the site can show baselines if desired.

```jsonc
{
  "schemaVersion": 1,
  "slug": "pong",
  "version": "v1.0.0",
  "name": "Pong",
  "difficulty": "easy",
  "tags": ["arcade", "2d"],
  "summary": "A two-paddle rally game.",       // nullable
  "description": "## Pong\n…",                  // nullable (resolved description.md body)
  "variants": [
    { "slug": "base", "name": "Base", "description": null }
  ],
  "checks": [
    { "view": "title", "name": "Title", "referenceView": "title" }
  ]
}
```

Only case-versions that have at least one published run need to be emitted, but
emitting every ingested version is also valid (and simpler); the site keys
lookups by `(slug, version)` from each run's `subject`.

## 4. Core-side backend client trait

Runners (CLI, worker, Tauri) resolve definitions through one trait in
`crates/core`. It mirrors today's catalog/version/reference resolution but
sources everything from the backend over HTTP instead of a checkout. The
existing `TestCaseCatalog` (filesystem) stays for local dev; this trait is the
remote source.

```rust
// crates/core/src/backend_client.rs (new)

use crate::error::Result;
use crate::run_record::{RunLinks, RunRecord};
use crate::review::Writeup;
use crate::test_case::{TestCase, TestCaseVersion};

/// A resolved container definition the runner builds locally.
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct ContainerDefinition {
    /// Harness slug this definition builds the image for.
    pub harness: String,
    /// Aggregate content hash over the whole build context. The runner tags the
    /// built image with this and reuses it until the hash changes (see below).
    /// Format: `sha256:<hex>`.
    pub content_hash: String,
    /// The harness this Dockerfile builds `FROM` within the cabinet, if any
    /// (e.g. a per-harness image `FROM` the shared `base`). `None` for `base`.
    pub builds_from: Option<String>,
    /// Every file of the build context, store-relative path -> bytes.
    pub files: Vec<ContainerFile>,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct ContainerFile {
    /// Path relative to the build-context root (e.g. `Dockerfile`).
    pub path: std::path::PathBuf,
    /// Raw file bytes.
    pub bytes: Vec<u8>,
}

/// A reference view resolved to its backend-rendered screenshot bytes. The
/// runner seeds these as visual targets and uses them as validation baselines;
/// it never receives the mockup HTML (rendering happens on backend ingest).
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct ResolvedReference {
    pub view: String,
    pub png_bytes: Vec<u8>,
}

/// One seeded artifact (a spec source or an asset file) fetched by key.
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct ResolvedArtifact {
    /// The store-relative `source` key (matches `SpecFile.source` / asset entry).
    pub source: std::path::PathBuf,
    pub bytes: Vec<u8>,
}

/// What runners use to resolve definitions from, and publish runs to, the backend.
#[async_trait::async_trait]
pub trait BackendClient: Send + Sync {
    /// The full catalog: cases and their versions. (`GET /test-cases`)
    async fn catalog(&self) -> Result<Vec<TestCase>>;

    /// Versions available for one case. (`GET /test-cases/{slug}/versions`)
    async fn versions(&self, slug: &str) -> Result<Vec<String>>;

    /// Resolve an exact, immutable test-case version manifest.
    /// (`GET /test-cases/{slug}/versions/{version}`)
    ///
    /// Returns a `TestCaseVersion` whose paths are store-relative keys (not host
    /// paths). The runner fetches spec/asset bytes via `artifact` and reference
    /// screenshots via `references` as it seeds.
    async fn resolve_version(&self, slug: &str, version: &str) -> Result<TestCaseVersion>;

    /// Fetch one seeded artifact (spec source or asset) by its `source` key.
    /// (`GET …/artifacts/{path}`)
    async fn artifact(
        &self,
        slug: &str,
        version: &str,
        source: &std::path::Path,
    ) -> Result<ResolvedArtifact>;

    /// Fetch the backend-rendered reference screenshots for a variant: the
    /// common references plus that variant's own. (`GET …/references/{scope}/{view}.png`)
    async fn references(
        &self,
        slug: &str,
        version: &str,
        variant: &str,
    ) -> Result<Vec<ResolvedReference>>;

    /// The prompt template source for a version (returned inline by
    /// `resolve_version` too; this is the explicit fetch).
    async fn prompt_template(&self, slug: &str, version: &str) -> Result<String>;

    /// Resolve a harness container definition. (`GET /containers/{harness}`,
    /// plus `…/files/{path}` for each file.)
    async fn resolve_container(&self, harness: &str) -> Result<ContainerDefinition>;

    /// Submit a published run: record + review + resolved links. (`POST /runs`)
    /// Idempotent on `record.id`.
    async fn publish_run(
        &self,
        record: &RunRecord,
        review: &Writeup,
        links: &RunLinks,
    ) -> Result<PublishAck>;
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct PublishAck {
    pub id: String,
    pub newly_published: bool,
}

/// Compute the aggregate content hash for a container build context. MUST match
/// the backend's recipe so a runner's tag agrees with the served `content_hash`:
///
///   1. For each file, compute `sha256(bytes)`.
///   2. Sort the `(path, sha256)` pairs by path (byte order, forward-slash
///      separators).
///   3. Feed each pair into a running SHA-256 as `"{path}\n{sha256hex}\n"`.
///   4. The aggregate is `"sha256:" + hex(digest)`.
```

### How the existing container layer consumes the served definitions

`crates/core/src/container.rs` today only starts/execs/collects against an image
name (`ContainerSpec.image`) and `run_once`s with `--pull never`. v0.2.0 adds a
local **build + cache** step in front of it, driven by the resolved definition:

1. Runner calls `resolve_container(harness)` → `ContainerDefinition` with its
   `content_hash`.
2. The runner computes the local image tag: `test-cabinet/<harness>:<content_hash-without-prefix>`
   (e.g. `test-cabinet/claude:1a7b…`). This **content-hashed tag** is what the
   run records as `RunEnvironment.containerImage` — replacing today's
   `test-cabinet/<harness>:latest`.
3. If an image with that tag already exists locally (a `<runtime> image inspect`
   check), it is **reused** — no rebuild.
4. Otherwise, the runner writes the definition's `files` into a temp build
   context and runs `<runtime> build -t <tag> <context>`. If `builds_from` is
   set, it resolves and builds that base first (same cache check), so the
   per-harness `FROM test-cabinet/base:<hash>` resolves locally. (Ingest may
   rewrite `FROM` lines to the hashed base tag, or the runner does; either way
   the served definition and the runner agree via `builds_from`.)
5. The built/cached `<tag>` is passed as `ContainerSpec.image` to the existing
   `CliContainerRuntime`; nothing downstream changes.

A new `core::container::ImageBuilder` (or method on the runtime) owns steps 2–4;
`CliContainerRuntime` gains `build_image(tag, context_dir)` and
`image_exists(tag)`. The image is cached across runs and only rebuilt when the
definition's content hash changes.

### Where reference rendering goes

`crates/core/src/reference.rs`'s `BrowserRenderer` (runner-side render of mockup
HTML) is **retired from the runner's resolve path**. Runners obtain rendered
screenshots from `BackendClient::references` and feed them to seeding and to the
`Validator` (which already takes `&[RenderedReference]`). The same render logic
moves into the backend's ingest step. The runner's headless browser is still
required for the load check and per-check capture.

All configuration is environment variables (no config file needed for v0.2.0).

| `TCAB_BACKEND_STORE` | no (default `./tcab-store`) | On-disk definition store: copied test-case versions, rendered reference PNGs, and container build contexts, keyed by slug/version and `(harness, contentHash)`. Immutable once written. | `/var/lib/tcab/store` |
| `TCAB_R2_ACCOUNT_ID` | yes | Cloudflare account id for the R2 bucket. | `abcd…` |

| `TCAB_R2_ACCESS_KEY_ID` | yes | R2 S3-API access key id (the only credential that can write the bucket). | `…` |

- The backend holds the **only** R2 write credential; the bucket is read-only to

  project than the snapshot/site; the backend is not involved in per-run build
  deploys (the operator's component runs `wrangler pages deploy` and captures the
  reported URL, which it then sends in `POST /runs.links.playableBuild`).

## 6. Consistency checks against existing code

- `RunRecord` / `RunMetrics` / `ValidationSummary` / `RunLinks` / `RunSubject` /
  `RunStatus` JSON in §1.4 and §3 is exactly `crates/core/src/run_record.rs` +
  `packages/run-record/src/index.ts` (camelCase). The backend stores and re-emits
  it verbatim — no field renames.
- `review.rating` tiers match `core::review::Rating` (`flawless|great|scuffed|broken`);
  `review.writeup` is the parsed `Writeup.body` (frontmatter stripped, as
  `parse_writeup` produces). The backend reconstructs `writeup.md` on the site
  side via the same `---\nrating: …\n---\n\n<body>` framing if needed.
- `CheckAction` in §1.2 is the internally tagged `{ "type": … }` form from
  `core::test_case::CheckAction` (matches `packages/browser-driver`).
- `containerImage` recorded in a run record becomes the content-hashed tag
  (`test-cabinet/<harness>:<hash>`), a concrete value the existing
  `RunEnvironment.containerImage` field already carries.
- `RunLinks.playableBuild` is the wrangler-reported deployment URL, not a
  constructed `<run-id>.<project>.pages.dev` host (per the resolved decision and
  to avoid Cloudflare's branch-alias sanitization/truncation).
